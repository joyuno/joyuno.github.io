오늘은 1.10 계열 릴리스를 준비하면서 걸린 문제 세 가지를 잡았다. 테스터 PC와 폰의 사용량 숫자가 서로 다르게 보인 문제, Windows에서 안드로이드 네이티브 빌드가 깨진 문제, 맥의 iOS 로컬 빌드가 옛 경로를 붙잡고 있던 문제다. 세 가지 모두 지금 코드가 아니라 어딘가에 남아 있던 옛 상태가 원인이었다.

## 테스터 PC와 폰의 사용량 숫자가 서로 달랐던 문제

테스터가 보내 준 화면에서 PC의 Lepons는 주간 사용량이 "100% 남음"이었고, 폰은 "87% 사용"이었다. 테스터의 실제 주간 사용량은 7%였다. 두 값 모두 틀렸다는 게 출발점이었다.

처음에는 PC 계산 로직이 잘못됐거나, 폰 쪽 캐시가 오래됐다고 의심했다. 그런데 두 화면이 같은 옛 값에서 출발한 것처럼 보였다. 그래서 숫자가 어디서 오는지부터 따라갔다.

Lepons는 Claude에 사용량을 직접 묻지 않는다. Lepons가 띄운 Claude Code 세션이 답할 때마다 상태줄로 넘어오는 값을 홈 폴더의 사용량 파일에 저장하고, PC가 그 파일을 읽는다. 테스터 PC의 파일에는 지난주에 받은 87%가 그대로 남아 있었다. 주간 한도는 이미 초기화됐는데, Lepons 안에서 Claude가 한 번도 답하지 않아 파일이 갱신되지 않은 것이다.

> 파일이 틀린 게 아니라 **멈춰 있었다**. 문제는 멈춘 값을 PC와 폰이 서로 다르게 해석한 데 있었다.

PC는 초기화 시각이 지난 기간을 "새 주가 시작됐으니 0% 사용"으로 보고 100% 남음으로 표시했다. 폰은 같은 옛 값을 그대로 87% 사용으로 보여 줬다. 두 화면이 서로 다른 규칙을 쓰고 있었던 것이다.

해결은 PC가 폰에 값을 보낼 때도 같은 규칙을 적용하는 것이었다.

| 구분 | 수정 전 | 수정 후 |
|---|---|---|
| 초기화가 지난 옛 값 | PC 100% 남음 / 폰 87% 사용 | 둘 다 0% 사용 |

이제 폰은 PC가 계산한 값을 받아 쓰므로 어디서 봐도 같은 숫자가 나온다. 리셋 규칙 테스트를 추가했고, PC 973개와 폰 137개 테스트가 통과했다.

다만 한계가 남는다. Lepons 안에서 Claude가 한 번 답하기 전까지는 0%가 보이고, 실제 7%는 그 뒤에야 맞게 나온다. 이 임시방편이 마음에 걸려서 1.10.2에서는 로컬 PC에 세션이 켜져 있을 때 `claude -p "/usage"`를 조회하도록 바꿨다. 시작할 때, 4시간마다, 초기화 직후에 한 번씩 부른다. 이 PC에서 실행해 보니 대화를 남기지 않고 5초쯤 걸려 사용량 줄이 나왔다. 5시간 한도 요금제의 출력 형식과 다른 언어 출력은 아직 확인하지 못했다. 출력을 읽지 못하면 기존 방식으로 돌아가게 해 두었다.

사용량 그래프가 안 뜨는 증상은 아직 원인을 못 찾았다. 이 PC에서는 1.5GB 기록을 2초에 계산하므로 계산 속도 문제일 가능성은 낮다고만 적어 둔다.

## Windows에서 안드로이드 빌드가 연달아 깨진 이유

안드로이드 릴리스 빌드를 이 Windows PC에서 돌렸더니 `react-native-worklets`의 CMake 단계에서 `mkdir ... No such file or directory`로 실패했다. 복사를 다시 하고 빌드를 돌리자 두 번째 문제가 나왔다.

두 번째는 디스크였다. 임시 빌드 복사본이 약 1GB를 차지하고 있었는데, 이걸 지우는 작업은 자동 안전 검사에 막혀서 직접 지우도록 남겨 두었다.

디스크 공간을 확보하고 다시 빌드하자 마지막 원인이 드러났다. `react-native-gesture-handler`의 생성 파일 경로가 Windows의 260자 제한을 넘었다. `C:\lb`로 옮겨도 이 경로 하나가 넘어서 해결되지 않았다.

> 이 PC에서는 Windows 경로 길이 제한을 피할 방법이 없었다. 남은 선택지는 맥에서 빌드하는 것뿐이었다.

맥에는 Android 빌드 환경이 이미 있었고, EAS 로컬 빌드로 서명 키를 직접 쓸 수 있었다. 맥에서 빌드해 versionCode 13을 만들었다. 다만 EAS submit은 Google 서비스 계정 키가 등록되어 있지 않아 비대화형 모드에서 실패했다. 그래서 AAB를 Play Console 비공개 테스트(Alpha)에 직접 올리고 검토를 요청했다.

## 맥 iOS 로컬 빌드가 옛 빌드 폴더를 기억하고 있던 문제

iOS 로컬 빌드는 두 번째 시도부터 DOM 번들링에서 실패했다. 로그에는 `Unable to resolve module`이 찍혀 있었고, 해석하려던 경로에 이전 빌드 폴더의 UUID가 들어 있었다. 실제 파일 `map-dom.tsx`는 현재 빌드 폴더에 있었다.

처음에는 모듈 해석 설정 문제로 봤다. 하지만 파일은 제자리에 있었기 때문에 해석 설정이 아니라 캐시를 의심하게 됐다. 확인해 보니 Metro의 변환 캐시가 옛 빌드 폴더 경로를 그대로 기억하고 있었다.

해결은 `$(getconf DARWIN_USER_TEMP_DIR)` 아래의 `metro-cache`와 `metro-file-map-*`를 지우고 다시 빌드하는 것이었다. 캐시는 다음 빌드 때 자동으로 다시 만들어진다. 이 조치 후 iOS 빌드가 성공해 TestFlight에 올라갔다(빌드 27).

같은 문제가 안드로이드 APK 빌드에서도 연달아 나왔다. 빌드를 바로 이어서 돌리면 옛 경로가 남는다는 점을 메모해 두었고, 같은 방식으로 캐시를 지우고 해결했다.

**남은 과제:** 맥 키체인이 원격 접속에서 잠겨 있어 Mac용 dmg 서명과 공증은 아직 못 했다. 잠금을 풀고 빌드하는 작업이 남아 있다.

### 오늘의 한줄
빌드와 표시 문제의 원인은 코드보다 **어딘가에 남아 있던 옛 상태**였다. 옛 사용량 파일, 옛 Metro 캐시, 옛 빌드 폴더가 그랬고, 같은 숫자나 같은 경로가 두 곳에서 다르게 보이면 먼저 두 쪽이 같은 옛 값을 읽고 있는지부터 확인하면 된다.
