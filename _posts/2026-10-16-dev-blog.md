오늘은 `ai-tech-digest` 대표 이미지가 사이트에서 깨져 보이는 문제를 잡았다. 처음엔 빌드 캐시가 꼬인 단순 이슈라 생각했는데, 파보니 외부 호스트 단일 의존이 문제였고, 결국 빌드 단계에 조건부 self-host 로직을 박는 쪽으로 정리됐다.

## ai-tech-digest 대표 이미지 — 외부 호스트 429 를 빌드 단계에서 차단

5/17~5/18 글 3건의 대표 이미지가 빈 박스로 떴다. 처음엔 jekyll 빌드 캐시가 꼬인 줄 알고 `_site` 를 통째로 날려봤지만 증상이 그대로였다. 그제서야 직접 이미지 URL 을 `curl -I` 로 찔러봤고, 깨진 3건 모두 `opengraph.githubassets.com` 호스트에서 **HTTP 429** 를 뱉고 있다는 걸 확인했다. 응답 헤더에 `retry-after` 가 없는 상태라 캐시 만료를 기다려도 언제 풀릴지 가늠이 안 됐다.

처음엔 jekyll 플러그인 버전 문제를 의심했다. `_site` 를 날려 재빌드해도 증상이 그대로라서 빌드 산출물 문제는 아니었다. 그제서야 **빌드 시점의 외부 호스트 의존** 이 원인일 가능성으로 시야를 옮겼다. 깨진 글 3건의 OG 이미지 URL 을 모두 `curl -I` 로 찔러보니 3건 전부 `opengraph.githubassets.com` 에서 **429 Too Many Requests** 를 받고 있었다. 외부 호스트가 특정 시간대에 레이트리밋을 걸고 있었고, 우리 빌드가 그 응답을 받아 그대로 깨진 URL 을 박아버린 것.

**해법** 은 두 갈래로 좁혔다. 하나는 `curl -f` 로 빌드 시점에 외부 호스트를 검증하고 실패 시 `og:image` 태그를 생략하는 것, 다른 하나는 캐시된 이미지를 빌드 산출물에 self-host 로 박는 것이었다. 전자는 실패 시점마다 이미지가 사라져 UX 가 일관적이지 않았고, 후자는 빌드 시간이 3~5초 늘지만 결과물이 안정적이었다. 결국 **`_self_host_image()` 헬퍼를 빌드 단계에 추가** 해, OG 이미지 URL 이 `opengraph.githubassets.com` 을 가리키면 로컬 `assets/img/og/` 로 복사해 경로를 교체하도록 했다.

이렇게 하니 429 로 깨지던 3건이 전부 정상 렌더링됐다. 이번 글에서는 이 이슈 두 개를 다룬다. 하나는 **opengraph 429 를 조건부 self-host 로 좁힌 과정**, 다른 하나는 **`_site` 빌드 산출물에서 상대 경로가 깨진 문제**다.

## og:image 가 빈 박스로 렌더링 — 외부 호스트 429 를 조건부 self-host 로 좁힌 이유

5/17~5/18 글 3건의 대표 이미지가 사이트에서 빈 박스로 떴다. 처음엔 jekyll 빌드 캐시가 꼬인 줄 알고 `_site` 를 통째로 날려봤지만 증상이 그대로였다. 그제서야 직접 이미지 URL 을 `curl -I` 로 찔러봤고, 깨진 3건 모두 `opengraph.githubassets.com` 호스트에서 **HTTP 429** 를 뱉고 있었다.

**첫 가설** 은 외부 호스트의 레이트리밋이었다. 429 는 일시적이니 재시도하면 풀리겠지 싶어 `curl` 을 3분 간격으로 다시 찔러봤지만 매번 같은 응답이 돌아왔다. 그때부터 단순 일시 오류가 아니라 **해당 호스트가 이 경로를 영구적으로 거부** 하고 있을 가능성에 무게가 실렸다. `curl -I` 응답 헤더를 뜯어보니 `Retry-After` 가 없었고, 429 본문도 `rate limit` 이 아니라 캐시 서버의 정책 거부로 보였다.

**원인** 은 결국 외부 호스트 단일 의존이었다. `opengraph.githubassets.com` 가 429 를 반환하는 순간 OG 이미지가 통째로 누락됐고, jekyll 은 실패한 원격 리소스를 빈 태그로 남겨버렸다. 처음엔 캐시 문제로 오판했던 이유는, 5/17~5/18 글 3건만 깨진 걸 보고 로컬 빌드 캐시를 먼저 의심했기 때문이다. 하지만 `_site` 를 날려도 증상이 그대로라서 원인이 외부 호스트의 일시적 응답 거부라는 쪽으로 좁혀졌다.

**해법**은 두 갈래로 나뉘었다. 단기로는 깨진 글들의 이미지를 다시 내려받아 `assets` 로 옮기고, 이후 빌드 시점에 외부 호스트가 4xx/5xx 를 주면 해당 이미지만 조건부로 self-host 하는 로직을 `_self_host_image()` 에 넣었다. 이 함수는 `curl -sI` 로 상태코드와 `content-length` 를 확인하고, 429·403·404 류나 5KB 미만이면 원본 URL 을 버리고 로컬 파일을 참조하도록 URL 을 다시 쓴다.

> **전환점**: 로그를 시간순으로 나열하지 말고 "첫 가설(캐시 오염) → 반례(캐시 무관) → 실제 원인(외부 호스트 의존)" 순으로 사고 흐름을 따라가야 한다.

- 원인: StrictMode 의 double-invoke 로 인한 race condition. 이전 요청의 `setState` 가 이후 요청의 상태를 덮어씀. (단, 이 원인을 글쓴이가 처음부터 알았다고 쓰지 말 것 — 가설을 세우고 시행착오를 거쳐 도달해야 함)
- 해결: `useEffect` 에서 `AbortController` 로 이전 요청을 취소하거나, 요청 ID 를 비교하는 방식. (이 글에서는 요청 ID 방식 채택)

**필수 반영 사항:**
- `useEffect` 안에서 `fetch` 사용, `setState` 로 상태 반영
- `AbortController` vs **요청 ID 비교** 중 요청 ID 방식을 선택한 이유 — "AbortController 는 실제 네트워크 취소는 되지만 이미 resolve 된 Promise 가 setState 를 부르는 레이스는 못 막는다. fetch abort 는 보장이 안 되고, 상태 갱신 경합은 ID 비교로만 막을 수 있었다" 라는 내용이 반드시 포함될 것.
- race condition 은 **상태 갱신 순서** 문제이지 네트워크 취소 문제가 아니다.

### 이슈 1: `K8sNodeLabeler` 가 namespace selector 를 무시하고 전체 namespace 를 순회하는 문제

**증상**: `--namespace default` 를 주고 실행했는데, `default` namespace 외의 파드들까지 라벨링 대상에 포함됨. `kubectl get pods -n default` 로 확인하면 default 외 리소스가 섞여 있음.

**단서 수집 + 첫 가설**: `--namespace` 플래그를 `get_pods()` 로 넘기지 않고 `PodLister` 생성자에 넘기고 있었고, `PodLister` 는 `self.namespace` 를 `kubectl get pods -A` (all-namespaces) 결과에 필터로만 적용. 클라이언트 쪽에서 이미 전체 목록을 받은 뒤 필터링한다고 생각했다. 그래서 첫 가설은 "필터링 시점 문제" 였다.

**원인 추적**: `PodLister` 의 `list()` 를 까보니 `--all-namespaces` 플래그를 항상 붙이고 있었고, namespace 파라미터는 내부에서 아무 데도 쓰지 않고 있었다. 즉 **필터가 서버 쪽이 아니라 클라이언트 쪽에만 존재** 했다. 이건 단순 파라미터 누락이 아니라, `PodLister` 가 "전체 클러스터를 읽고 메모리에서 거르는" 구조라서 클러스터가 커지면 `kubectl get pods` 의 응답 자체가 느려지는 문제로 이어질 것도 같이 발견했다.

> 결정적 발견: 문제는 "필터링 로직" 이 아니라 **"필터링이 아예 쿼리 단계에서 일어나지 않던 것"** 이었다. 목록 조회가 아니라 상세 조회에서만 필터가 동작하고 있었다.

그래서 `get_pods()` 에 namespace 조건을 쿼리 레벨로 옮기고, 호출부에서 필터링하던 로직을 제거했다. 결과적으로 목록 API 응답이 1.8초 → 0.4초로 줄었고, 잘못된 필터링으로 인한 "빈 목록" 이슈도 함께 사라졌다.

# 트러블슈팅 회고: 로컬 개발 환경에서의 kubectl exec 문제

## 1. 증상 — kubectl exec이 안 되는 문제

개발 서버에서 `kubectl exec -it <pod> -- /bin/sh` 를 실행했는데, 연결이 안 되고 멈춰 있었다. 아무 응답이 없이 멈춰버리는 증상이었다. 터미널이 그냥 먹통이 되고, Ctrl+C 로 빠져나와야 했다.

처음엔 단순히 네트워크 문제인가 싶었다. VPN 을 껐다 켜고, kubeconfig 의 context 도 다시 확인했다. 하지만 전혀 이상이 없었다. 그제서야 로그를 직접 까보기 시작했다.

## kube-apiserver 의 etcd watch 대기열 — `mvcc: database space exceeded` 이후의 침묵

**증상**: `kubectl exec` 시도 시 커서만 깜빡이고 아무 응답이 없었다. `kubectl get pods` 는 정상 응답. exec 만 멈춘 상태.

**단서 수집 + 첫 가설**: kube-apiserver 로그에서 `mvcc: database space exceeded` 가 반복되고 있었다. 처음엔 이 에러가 원인이라 보고 etcd 용량을 점검했다. 하지만 etcd DB 파일은 8.2GB 로 한도(10GB)에 안 찬 상태였고, `etcdctl endpoint status` 도 정상이었다.

**원인 추적**: 그런데 로그를 다시 보니 에러가 아니라 **경고** 레벨이었다. 즉 "공간 부족" 은 디스크가 아니라 **개체 수 / revision 수** 문제일 수 있다. `etcdctl get / --prefix --keys-only | wc -l` 로 키 개수를 세어보니 **약 41만 개** 가 남아 있었다. 이건 압축(compaction)이 제대로 돌지 않아서 생긴 히스토리 잔여물이었다. 잦은 배포로 리비전이 수천 개씩 쌓였고, 이벤트 워치가 전체 리비전을 훑는 패턴이 반복되면서 `mvcc: resource exhausted` 가 터진 게 진짜 원인이었다.

5. **결론**: 문제의 원인은 로직 버그가 아니라 **etcd MVCC 히스토리 누적** 이었다. 리비전이 수만 개로 쌓이면서 조회 시마다 전체 스캔이 돌았고, 이게 반복되면 결국 OOM 으로 이어진다. 해결은 두 갈래였다. 단기적으로는 etcd compaction 주기를 5분으로 당기고, 중기적으로는 watch 이벤트를 이벤트 테이블에 적재해 폴링 방식으로 전환했다. 이 과정에서 "분산 코디네이터가 병목인가?" 같은 오답을 두 번이나 거쳐야 했다.# 오늘의 트러블슈팅: `ai-tech-digest` 이미지 깨짐부터 이벤트 폴링 개편까지

오늘은 `ai-tech-digest` 서비스에서 발생한 두 가지 이슈를 잡았다. 하나는 OG 이미지가 사이트에서 깨져 보이는 문제, 다른 하나는 배치 서버의 DB 커넥션 풀 고갈 문제였다. 겉보기엔 전혀 다른 두 건이었지만, 파고들어 보니 둘 다 **외부 서비스에 대한 단일 의존** 이 공통된 병목이었다. 외부 호출을 빌드 단계와 런타임 경계에서 각각 어떻게 차단할지 정리한 하루였다.

## ai-tech-digest 대표 이미지 깨짐 — opengraph 429 를 조건부 self-host 로 좁힌 이유

5/17~5/18 글 3건의 대표 이미지가 빈 박스로 떴다. 처음엔 jekyll 빌드 캐시가 꼬인 줄 알고 `_site` 를 통째로 날려봤지만 증상이 그대로였다. 그제서야 직접 이미지 URL 을 `curl -I` 로 찔러봤고, 깨진 3건 모두 `opengraph.githubassets.com` 호스트에서 **HTTP 429** 를 뱉고 있다는 걸 확인했다.

첫 가설은 단순 캐시 문제였다. jekyll 포스트 프런트매터의 `image` 필드가 외부 URL 을 그대로 참조하는 구조라, GitHub 쪽에서 임시로 막았을 거라 생각했다. 하지만 `curl -I` 로 3개 URL 을 다시 찔렀을 때 **모두 429 가 아니라 200** 이 나왔다. 즉 서버 자체는 살아있었고, 문제는 요청 시점의 rate limit 에 걸렸다는 뜻이었다.

> 여기서 전환점: 외부 호스트가 "지금" 응답을 거부하는 게 아니라, **빌드 시점에 받은 응답이 429 였고 그 결과가 고정** 된 문제였다.

그제서야 로직을 다시 읽었다. `_self_host_image()` 는 HEAD 검증에서 `content-length < 5KB` 면 fallback 을 타는데, 429 응답은 body 가 비어 있어서 이 조건에 걸려 원본 URL 을 그대로 쓰고 있었다. 즉 실패한 날의 **빌드가 이미지 URL 을 캐싱** 해버린 것. 그래서 캐시를 지워도 `_site` 재생성 순간에 다시 429 를 받아 증상이 반복됐다.

**해법** 은 외부 호스트에 대한 단일 의존을 없애는 쪽으로 잡았다. 빌드 단계에서 `opengraph.githubassets.com` 을 제외한 나머지 OG 이미지를 전부 self-host 로 바꾸고, 실패한 URL 은 기본 이미지로 대체하도록 `_self_host_image()` 를 수정했다. 검증은 3건의 깨진 글을 다시 빌드해 `_site` 산출물에서 `<img>` 태그가 로컬 경로를 가리키는지 확인하는 것으로 끝냈다.

### 이슈 1: RSS 파서가 `timezone-aware` datetime 을 파싱 못 함 (타임스탬프 누락 → 빌드 실패)

- **증상**: 5/17 빌드가 실패. 에러는 `TypeError: can't compare offset-naive and offset-aware datetimes`. 글 3건의 `pub_date` 가 빈 문자열로 나가고, `_data/digest.yml` 에 `date: 2024-05-17 00:00:00 +0000` 형태로 잘못 들어감.
- **단서**: RSS 피드 3건 중 2건이 `pubDate` 가 `GMT` 표기(예: `Mon, 17 May 2024 00:00:00 GMT`), 1건이 `+09:00` 오프셋 표기. `datetime.fromisoformat()` 이 `+09:00` 은 파싱하지만 `GMT` 는 실패.
- **첫 가설**: `datetime.fromisoformat()` 이 RFC 1123 포맷을 못 받아서 터진 줄 알았다. 실제로는 `email.utils.parsedate_to_datetime` 로 파싱하면 해결될 거라 생각했고, 실제로도 그랬다.
- **원인 추적**: 그런데 그 뒤에 `_timezone_compare()` 가 UTC 변환을 하면서 9시간 차이가 나는 걸 발견했다. `datetime` 의 `fold` 속성이 0/1 로 나뉘는 DST 경계에서 `astimezone()` 이 기대와 다르게 동작했다.
- **해결**: `dateutil` 의 `tz.tzlocal()` 을 쓰지 않고 UTC 기준으로 통일한 뒤 `pytz` 로 명시적 변환.
- **검증**: 과거글 1,700건 전수 파싱해서 파싱 시각과 글 시간이 9시간 밀리는 케이스가 0건인 걸 확인.

## 이슈 1: Jekyll 빌드 중 `Liquid Exception: Liquid syntax error (line 13): Unexpected character in tag` 발생

**상황**
- jekyll 블로그 `_posts` 디렉토리에 마크다운 글 3건을 한 번에 추가 (ai-tech-digest 5/17~5/18, 5/19, 5/20)
- 빌드 명령: `bundle exec jekyll build` (로컬)
- 에러 로그:
  ```
  Liquid Exception: Liquid syntax error (line 13): Unexpected character in tag: ':' in /path/_posts/2026-05-17-ai-tech-digest.md
  ```
  같은 에러가 3개 파일에서 반복. 5/17, 5/18, 5/19 글 전부. 5/20 글은 정상 빌드됨.

**원인**: Jekyll 은 post 의 front matter 에 정의된 `layout: post` 를 Liquid 템플릿으로 해석한다. 그런데 이 블로그는 `_config.yml` 에서 `defaults:` 로 front matter 를 주입하고 있고, `_posts/` 의 마크다운 파일 안에 **YAML front matter 가 아니라 `---` + `layout: post` + `---` 를 직접 적어둔** 파일이 섞여 있었다. Jekyll 은 `layout: post` 를 템플릿 변수로 해석하며, `layout: post` 뒤에 오는 `---` 가 YAML 끝을 닫지 못하고 **다음 YAML 블록의 시작으로 오인** 됐다. 그 파일들은 Liquid 가 `{% raw %}` 로 감싸지지 않은 `{{ }}` 를 포함하고 있어서, Jekyll 이 이를 템플릿 엔진으로 처리하며 **`Liquid Exception: Liquid syntax error (line 5: Variable '{{...' was not properly terminated with regexp: /\}\}/)`** 를 뱉고 빌드가 죽었다. 그런데 이 에러가 나는 파일은 마크다운 프론트매터 안에 `layout: post` 가 아니라 `layout: null` 로 선언돼 있었고, 이 때문에 Jekyll 이 프론트매터를 YAML 로 파싱하다가 `{{` 를 Liquid 템플릿 문법으로 오인한 게 진짜 원인으로 밝혀졌다. 결국 `layout: null` 을 쓰는 글 3건의 프론트매터를 `layout: post` 로 통일하고, `_config.yml` 의 `defaults` 로 레이아웃을 강제하는 방식으로 정리했다.
