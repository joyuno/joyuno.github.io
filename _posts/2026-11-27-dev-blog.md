오늘은 Lepons 대화 화면 하나를 붙잡고 네 군데를 팠다. 답변 속 이미지 경로가 PC 로그인 정보를 실어 나르던 문제, 원격 칸에서 보낸 글이 흔적도 없이 사라지던 문제, 터미널보다 한 박자 늦게 뜨던 화면, 그리고 `/` 목록에 스킬이 절반만 뜨던 문제다. 앞의 둘은 검토에서 걸린 보안·입력 사고였고, 뒤의 둘은 "왜 이렇게 느리고 왜 이렇게 빠졌나"를 파고든 쪽이다. 네 개 다 원인이 처음 짚은 곳과 달랐다.

## Lepons 대화 화면 — 답변 속 이미지 경로가 PC 로그인 정보를 실어 나르고 있었다

검토에서 지적이 하나 올라왔다. 이때 Windows가 PC의 로그인 정보를 자동으로 보낸다. 그림을 보여주기만 해도 자격증명이 넘어간다는 뜻이라 심각으로 분류했다.

처음엔 이미지 렌더링만 막으면 되겠지 싶었다. 그런데 코드를 따라가 보니 문제는 렌더링이 아니라 경로 해석이었다. 화면 쪽이 경로를 그대로 이미지 소스로 넘기고, 앱 본체가 그 경로를 읽어 데이터를 돌려주는 구조였다. 한 군데만 막으면 다른 길로 샌다.

**해법**은 두 군데에 같은 규칙을 넣는 것이었다. 이 PC 드라이브 경로와 세션 폴더 안의 파일만 그림으로 보여주고, 나머지는 글자로만 남긴다. 화면 쪽과 앱 본체 쪽 양쪽에 같은 판정을 심었다. **검증**은 이상한 경로 12가지를 만들어 넣는 방식으로 했다. 전부 막히거나 이 PC 드라이브 경로로만 바뀌었다.

> 이미지에서 막은 그 입력이 링크로도 나가고 있었다. `file:////서버/공유/파일`을 Ctrl+클릭하면 같은 일이 벌어졌다.

4~5묶음 검토에서 나온 지적이다. 이미지에 쓴 규칙을 링크 열기에도 그대로 적용했다. 한 곳을 막았을 때 "같은 입력이 다른 출구로도 나가는가"를 같이 봤어야 했는데, 이미지에서만 확인하고 끝낸 게 아쉬웠다.

## Lepons 원격 세션 — 보낸 글이 사라진 건 입력 통로가 아니라 tmux 스크롤 모드였다

원격 칸에서 대화 화면 입력창으로 글을 보냈는데 아무 일도 안 일어났다. 터미널 화면으로 바꿔 봐도 글이 없었다. 로컬은 멀쩡하고 원격만 그랬다.

첫 가설은 "질문이 떠 있다고 잘못 판단해서 입력을 막았다"였다. 그 경우엔 "위 질문에 먼저 답해 주세요"가 떠야 하는데 안 떴다고 확인돼서 바로 버렸다. 두 번째로 의심한 건 원격 칸의 입력 통로였다. 원격 tmux 칸은 키 입력을 잠깐 모아 보내는 장치가 따로 있어서, 입력창이 그 길을 안 타고 엉뚱한 칸이나 끝난 연결로 보냈을 수 있다고 봤다.

진짜 원인은 그 옆에 있었다. 원격 칸을 마우스 휠로 위로 올리거나 글자를 드래그해 선택하면 tmux가 **스크롤 보기 모드**에 들어간다. 이 모드에서는 들어오는 글자를 입력이 아니라 이동 키로 받아들인다. 그래서 보낸 글이 오류도 없이 사라진다. 터미널 화면에도 흔적이 없던 것과 맞아떨어진다.

**해법**은 보내는 순서를 바꾸는 것이었다. 먼저 스크롤 모드를 빠져나오고, 글을 넣고, Enter를 친다. 가짜 원격 환경에서 글과 Enter가 순서대로 도착하는지 테스트로 못박았다. 같이 손본 것도 있다.

- 원격 PC 하나당 SSH 연결 하나를 열어 두고 터미널과 기록 읽기가 같이 쓰게
- 원격에서 0.25초마다 기록을 지켜보다 새 줄만 흘려보내게
- 원격 셸이 출력하는 잡음과 기록 경로를 구분
- 실패하면 "기록을 찾지 못했어요", "연결이 끊겼어요"처럼 이유를 보여주게

**한계**는 분명히 남겼다. 이 PC에 tmux가 없어서 실제 copy mode를 재현하지는 못했다. 원인은 짐작이고, 순서 변경과 도착 테스트까지만 확인한 상태다. 실제 서버에서 칸을 일부러 스크롤해 둔 채 보내보는 확인이 아직 남아 있다.

## Lepons 대화 화면 반응 속도 — 2.5초 폴링을 버리고 파일 변경 알림으로 바꿨다

대화 화면이 터미널보다 한 박자 늦었다. 기록 파일을 2.5초에 한 번만 읽고 있었으니까. 처음엔 "간격을 0.5초로 줄이자"였다. 그런데 곰곰이 보면 정해진 간격으로 확인할 이유가 없다. 아무 일도 없는데 0.5초마다 파일을 보는 건 순수한 낭비다.

**해법**은 파일이 바뀌는 순간 운영체제가 알려주는 방식으로 갈아탄 것이었다. 대화가 길어지면 한 번 읽는 비용이 커지니, 기준을 먼저 정해 뒀다. 5MB 기록에서 한 번 읽는 데 30ms를 넘으면 새로 붙은 줄만 읽는 방식으로 바꾼다.

| 항목 | 결과 |
|---|---|
| 반응 속도 | 짧은 대화 0.13초 / 5MB 0.16초 / 20MB 0.22초 (전에는 평균 1.2초) |
| 5MB 다시 읽기 | 25ms — 기준 30ms 아래라 증분 읽기는 넣지 않음 |
| 8칸 동시 | 초당 22줄을 붙여도 놓친 줄 0, 칸당 CPU 2% |
| 병목 | CPU 한 코어 속도. 메모리·코어 수·디스크는 여유 |

**남은 과제**는 이 방식이 이 PC의 Claude 세션에만 붙었다는 점이다. Codex·OpenCode는 기록 저장 방식이 달라서 2.5초 간격 그대로고, 원격은 5초였다. 원격은 앞 섹션의 SSH 연결 재사용과 원격 감시로 따로 처리했다.

## Lepons `/` 명령 목록 — 폴더를 직접 훑던 방식을 버렸더니 신뢰 확인 구멍이 드러났다

`/`를 쳤을 때 스킬과 플러그인 명령이 일부만 떴다. 원인은 두 개였다.

1. 목록을 내가 폴더에서 직접 훑어 만들고 있었다. 스킬 폴더 하나가 다른 폴더를 가리키는 바로가기였는데 스캔이 바로가기를 따라가지 않아 통째로 건너뛰었다. MCP 명령은 서버를 실제로 켜야 알 수 있어서 처음부터 목록에 없었다. 플러그인이 설명 파일에서 명령 위치를 따로 정해 두면 그것도 못 읽었다.
2. 40개 제한. 플러그인 16개에 스킬까지 합치면 금방 넘는다.

**해법**은 목록을 Claude에게 직접 받아오는 것으로 바꿨다. 터미널에서 `/`를 쳤을 때 나오는 목록과 같다. AI를 부르지 않아서 토큰을 쓰지 않는 것도 재서 확인했다. 40개 제한도 없앴다.

> 목록을 받으려고 Claude를 잠깐 띄우는데, 그때 "이 폴더를 믿을까요?"를 건너뛰고 있었다.

이 해결이 더 큰 구멍을 만들었다. 대화 화면을 열기만 해도 그 폴더에 든 MCP 서버나 도우미 명령이 실행될 수 있었다. Windows에서는 폴더 안에 `claude.cmd`를 심어 두면 진짜 대신 그 파일이 실행될 수도 있었다. 그래서 다시 고쳤다.

- Claude에서 이미 신뢰한 폴더에서만 목록을 묻는다
- 프로그램은 항상 정해진 설치 위치에서 찾아 실행한다
- 묻는 시점은 `/`를 쳤을 때로 미루고, 한 PC에서 한 번에 하나씩만
- 설정이나 플러그인이 바뀌었거나 30분이 지났을 때만 갱신한다

재검토에서 또 걸렸다. **신뢰 범위가 Claude보다 넓었다.** Claude는 git 저장소 안이면 저장소 맨 위에서 멈추는데, 나는 디스크 맨 위까지 거슬러 올라갔다. 그래서 `~/projects`를 한 번 신뢰해 두면 그 아래 새로 받은 저장소까지 신뢰로 봤다. Claude 판정 코드를 직접 읽어서 똑같이 맞췄다. 3회차에서는 `.git`이 다른 곳을 가리키는 바로가기일 때(Google repo 도구나 Windows 정션이 그렇다) 그걸 건너뛰고 더 위로 올라가는 것까지 잡았다. `.git`이 보이면 바로가기든 아니든 거기서 멈추게 했다. 더 좁게 믿는 쪽이라 안전하다.

**검증**은 폴더에 `claude.cmd`를 심어 두고 목록을 받아와도 그 파일이 실행되지 않는 것을 테스트로 확인했다. 관련 테스트 403개 중 395개 통과, 실패 0(8개는 원래 건너뛰는 테스트).
