오늘은 세 가지를 잡았다. 자동 지원이 조용히 멈춰 있던 알림 문제, 원격 tmux 스크롤에 같은 출력이 쌓이던 문제, 폰에서 사진·파일 첨부가 실패하던 문제다. 첫 번째는 코드를 읽자마자 원인이 보였고, 두 번째는 세운 가설이 틀려서 한 번 갈아엎었고, 세 번째는 안드로이드와 아이폰의 원인이 서로 달랐다.

## 자동이력서지원 — '지원 안 함'으로 끝난 실행은 대화상자도 푸시도 없이 사라졌다

자동 지원을 걸어 두면 최종 검토 단계까지 가지도 못하고, 끝났다는 알림도 뜨지 않는다는 걸 확인했다. 먼저 폴러가 죽었는지부터 봤는데 `launchctl print` 결과는 `runs = 8485`, `last exit code = 0`, `state = not running`이었다. 폴러는 정상 종료했고, 대기열도 비어 있었다. 프로세스가 안 도는 게 문제가 아니었다.

단서는 실행 로그에 있었다. `apply_b3f463cc1d2d_1121-1048.out`에 `"status": "blocked"`가 찍혀 있었고, 사유는 Workday 지원서 4/6단계의 평판조회 동의가 필수 항목이라 '아니오'를 고르면 "채용 절차 진행 불가"가 뜨고, 이전 직장 조회를 하지 않는다는 규칙에 걸려 중단된 상태였다. 제출한 것은 없었다. 그런데 Redis 상태는 11-21 15:56 이후 `blocked`에서 한 번도 바뀌지 않았다.

여기서 처음 든 생각은 "상태가 안 넘어가서 멈춘 거 아닌가"였다. 그래서 `cal.py`의 상태 분기를 따라갔다. 358행이 `if s['status'] == 'ready':`였고, 363행은 blocked·failed일 때 콘솔에 한 줄 찍는 게 전부였다. `apply.sh`의 `popup()`도 ready 경로에서만 호출된다. 폰 푸시는 코드 자체가 없었다.

> 대화상자는 '제출 직전'에서만 뜨고, '지원 안 함'·'실패'는 권한 없는 앱의 배너 한 줄이 전부였다.

**해법**은 `apply.sh`를 고쳐 결과 종류와 무관하게 맥 대화상자와 폰 푸시가 모두 가게 만드는 것이었다. 원본은 `apply.sh.bak_1123`으로 남겼다. 다른 선택지로 상태 분기를 `cal.py` 쪽에서 바꾸는 안도 있었지만, 알림은 실행 껍데기의 책임이라 `apply.sh` 한 곳에서 끝내는 쪽을 골랐다.

**검증**은 문법 검사 통과, 그리고 삼일 결과 문구로 테스트 푸시를 보내 기기 1대에 도착하는 것까지 확인했다. 실제 자동 지원을 처음부터 끝까지 돌려서 대화상자와 푸시가 오는지 확인하지는 않았다. 삼일 건은 평판조회 동의 없이는 진행이 안 되니, 예외 승인 여부를 정하기 전까지는 같은 지점에서 다시 멈춘다.

## Lepons — 원격 tmux에 같은 출력이 쌓인 건 클라이언트 충돌이 아니라 11x5로 잘못 전달된 창 크기 때문이었다

증상은 이랬다. 5분할 중 하나를 닫고 스크롤하면 같은 줄이 여러 번 보이고, 입력창이 위로 밀린 것처럼 보였다. 처음 세운 가설은 "한 세션에 크기가 다른 클라이언트가 둘 붙어서 창 크기를 서로 뺏는다"였다. Lepons가 tmux에 `window-size latest`를 걸어 두기 때문에, 살아 있는 화면이 둘이면 마지막 입력이 온 쪽으로 창이 계속 바뀔 거라고 봤다.

Docker에 tmux 3.3a와 Claude Code 2.1.330을 설치하고 Lepons와 같은 터미널 설정으로 재현했다.

| 상황 | 결과 |
|---|---|
| 화면 하나, 50x30 → 100x40 | 깨끗함 |
| 전체 화면 모드를 끈 경우 | 깨끗함 |
| 100x40·50x30 두 화면을 번갈아 스크롤 | 창이 100x39 ↔ 50x29로 오감, 기록 66줄 → 219줄, 같은 답변 5~7번 반복 |

가설대로 재현은 됐다. 그래서 맥북에서 `tmux list-clients`를 받아 봤는데, 세션 4개 모두 붙어 있는 클라이언트가 정확히 하나씩이었다. **가설 기각**이다. `attach -d`로 고치는 안은 근거가 사라져서 접었다.

대신 그 출력에서 다른 게 눈에 걸렸다. 세션 세 개의 pane 크기가 `11x5`로 찍혀 있었다. 터미널로 쓸 수 없는 크기다. Lepons는 터미널 크기를 화면에서 재서 원격 tmux로 보내는데, 지도나 워크플로 화면이 터미널 영역을 가리고 있을 때 재면 그 쓰레기 값이 나온다. 이미 알려진 문제라 한 경로에는 막는 조건이 있었지만, 화면을 다시 그리는 `renderPanes`와 `showPlaced` 두 곳에는 그 조건이 빠져 있었다.

> 클라이언트가 둘이어서가 아니라, 안 보이는 터미널의 크기를 재서 11x5를 보내고 있었다.

맥북의 Claude Code는 `alt=0`, 즉 전체 화면 모드가 아니었다. 이 모드에서는 폭이 바뀔 때마다 대화 전체를 그 폭으로 다시 출력한다. 11칸으로 줄 때 한 번, 원래 폭으로 돌아올 때 또 한 번 다시 출력되고 그게 tmux 기록에 쌓인다. 반복 줄 수(`dup`)가 474, 262, 186으로 나온 게 그 흔적이었다.

**해법**은 `cockpit/src/renderer/main.ts` 두 곳에서 터미널 영역이 숨겨져 있을 때는 크기를 재지도, 보내지도 않게 하는 것이었다. 터미널로 돌아올 때는 지금처럼 다시 재서 올바른 크기를 보낸다. 타입 검사는 통과했고, 실제 맥북 원격 세션에서는 아직 확인하지 못했다. 이미 쌓인 줄은 그 세션을 새로 열어야 사라진다.

## Lepons — 폰 첨부 실패, 안드로이드는 연결 복귀를 기다리지 않았고 아이폰은 모달이 닫히기 전에 피커를 열었다

안드로이드는 "PC로 보내지 못했어요"가 떴고, 아이폰은 첨부 칩 자체가 생기지 않았다. 증상이 달라서 원인도 따로 봤다.

안드로이드 쪽은 코드에서 바로 잡혔다. 사진첩·파일 선택 화면은 안드로이드에서 별도 화면으로 열리고, 그동안 React Native는 앱을 백그라운드로 판단한다. 앱은 백그라운드가 되면 중계 연결을 일부러 끊고 돌아오면 다시 붙는데, 복귀 직후 업로드가 곧바로 `request()`를 호출한다. `mobile/src/relay/client.ts:146`이 `link?.phase !== "open"`이면 기다리지 않고 `offline`으로 거절한다. 재연결에 걸리는 1~2초가 그대로 실패가 됐다. 일반 메시지는 `/api/input`에 대해 연결 복귀를 기다리는 처리가 이미 있었는데, 업로드 경로에만 빠져 있었다.

아이폰은 코드상 추정이다. 클립 메뉴는 Modal이고, 항목을 누르면 `setPicker(undefined)`로 닫으면서 곧바로 사진첩을 연다. iOS는 모달 닫힘 애니메이션 중에 다른 화면을 present하면 무시하는 경우가 있고, React Native는 그 완료 신호(`onDismiss`)를 iOS에서만 준다. 그 신호를 안 쓰고 있었으니 선택 결과가 앱에 오지 않고 칩도 오류 문구도 안 생긴다.

**해법**은 세 가지였다. 업로드 전 최대 5초 연결 복귀 대기, `onDismiss` 뒤에 피커 열기(신호가 안 오면 1초 폴백), 그리고 입력란 위에 따로 떠 있던 칩 줄을 없애고 입력란 안쪽 타일로 옮기는 것. 사진은 썸네일, 파일은 아이콘과 파일명으로 보이고, 업로드 중에는 로딩이 겹치고 실패하면 빨간 테두리와 사유가 한 줄 붙는다. 타일을 누르면 폰 기본 미리보기로 열린다.

**검증**은 타입 검사와 폰 테스트 159개 통과까지였다. 웹으로 화면을 띄워 보려 했지만 `@xterm/headless` 때문에 웹 빌드가 원래 안 되는 프로젝트라 못 봤고, 실제 기기에서도 아직 확인하지 못했다. 다음 빌드로 실기기에서 사진·카메라·파일을 각각 눌러 봐야 한다.
