## `ai-tech-digest` 대표 이미지 깨짐 — opengraph 429 를 조건부 self-host 로 좁힌 이유

5/17~5/18 발행 글 3건의 대표 이미지가 사이트에서 빈 박스로 떴다. jekyll 빌드 로그에는 에러가 없었고, HTML 소스에는 `<img>` 태그는 있는데 브라우저가 403 을 뱉는 상태였다. 처음엔 단순 캐시 문제라 생각했다.

**첫 가설**은 Cloudflare 캐시였다. 이미지 URL 이 외부 호스트라서 브라우저 캐시가 stale 버전을 들고 있을 거라 짐작했다. 그래서 캐시 무효화 헤더부터 확인했는데, 응답 헤더는 정상이었고 실제로 curl 로 다시 가져와 보니 외부 호스트가 `429 Too Many Requests` 를 반환하고 있었다.

여기서 중요한 건 **429 가 특정 이미지에서만** 발생했다는 점이다. 같은 페이지의 다른 OG 이미지는 정상 로드됐다. 그 차이를 보니, 깨진 이미지들은 모두 `og:image` 가 외부 호스트(예: 원문 사이트의 CDN)를 직접 가리키는 경우였다. 즉 jekyll 이 내려받아 self-host 하는 로직이 아니라, 원문의 이미지 URL 을 그대로 쓰는 케이스였다.

**원인** 은 외부 호스트가 특정 시간대에 rate limit(429) 을 반환했고, 우리 페이지는 외부 이미지 URL 을 직접 `<img src>` 로 노출하고 있었던 것. 처음엔 CDN 캐시 만료로 판단했지만, `curl -I` 로 같은 URL 을 직접 때려보니 헤더에 `x-ratelimit-remaining: 0` 이 찍혀 있었다. 캐시 문제가 아니라 **우리 쪽 요청이 아니라 외부 호스트의 정책** 이 원인이었다.

- **검증**: `curl -I` 로 429 확인 → 외부 호스트 직접 호출 시 `x-ratelimit-remaining: 0`
- **해법**: 빌드 단계에서 OG 이미지를 내려받아 `/assets/img/` 로 self-host. 실패 시에만 외부 URL fallback.
- **남은 과제**: 원본 호스트의 이미지가 바뀌면 갱신 안 되는 문제 — 주기적 re-fetch 배치 고려 중.

이 톤과 구조를 **그대로 따라** 새 글을 쓰세요.

> | 실패 모드 | 사이트 로드 후 빈 박스 | 빌드 로그에 실패 목록 출력 |

## 글감 (기술적 사실)

- 주제: `ai-tech-digest` 개인화 추천 기능 구현 중 겪은 트러블슈팅 2건
- 이슈1: 개인화 추천에서 `category` 가 `undefined` 로 노출되는 문제
  - 증상: 추천 API 응답 JSON 에서 `category` 필드가 `undefined` 로 내려옴. UI 에서 `[object Object]` 로 렌더링.
  - 1차 가설: 응답 DTO 매핑 실패로 `category` 가 누락됐다고 생각. 실제로는 `category` 컬럼이 DB 스키마에 없었고, `category` 필드는 `JOIN` 으로 가져오는 파생 필드였음.
  - **원인**: `recommendations` 테이블에 `category` 컬럼이 없었음. `SELECT` 쿼리에 `r.category` 를 직접 참조했고, `LEFT JOIN` 대상인 `items` 테이블의 컬럼명이 `category_name` 이었음. `items.category_name` 을 `AS category` 로 매핑했어야 하는데 누락.
  - **해결**: `recommendations` 테이블은 그대로 두고, 조회 쿼리에서 `i.category_name AS category` 로 명시적 매핑. `repositories` 테이블의 `full_name` 조인 조건도 함께 확인.
  - 검증: 같은 쿼리로 재실행, `category` 필드 정상 반환 확인. 마이그레이션 불필요.

  2. **`recommendations` 생성 배치 — `ON DUPLICATE KEY UPDATE` 의존이 만든 유령 이력**
  - 증상: 배치가 돌 때마다 `updated_at` 이 매번 갱신되는데, 정작 데이터는 안 바뀐 것처럼 보임.
  - 단서: `SELECT * FROM recommendations WHERE ...` 로 dump 떠보니 `updated_at` 이 1분 단위로 계속 찍히고 있음. `created_at` 은 유지.
  - 첫 가설: 뭔가가 배치를 두 번 실행 중 (cron 중복 실행).
  - 원인: `ON DUPLICATE KEY UPDATE` 에서 `updated_at = NOW()` 가 매번 갱신되고, `source_key` 가 매번 새 UUID 라서 **upsert 가 매번 insert 로 빠지는** 구조.
  - 해결: 업데이트 시 `source_key` 를 고정하거나, `INSERT ... ON DUPLICATE KEY UPDATE` 의 중복 판정 키를 `(source_type, source_id)` 복합 유니크로 변경. 결과적으로 `updated_at` 이 실제 변경 시에만 갱신되도록.

## 주제 (하나의 글에 모두 포함)

주제 1: `ai-tech-digest` 의 **대표 이미지 깨짐** — 외부 호스트가 반환하는 `Content-Type: text/html` 을 이미지로 처리하려다 실패하는 문제. 처음엔 단순 캐시 문제로 보고 외부 호스트를 의심했다. 이후 **HTTP HEAD 요청 + content-type 검증을 추가**해 이미지가 아닌 응답을 걸러냈고, **이미지 바이트를 빌드 시점에 로컬로 가져오는 self-host** 로 최종 정리했다. (최종본에서 이 문제를 "실패에서 성공으로" 한 흐름으로 완성할 것)

6. **문제의 코드 위치**: `_self_host_image()` 헬퍼 함수, `build()` 메서드에서 `_self_host_image()` 호출 지점, `_fetch_url_content()` 헬퍼.

7. **문제의 코드**: `_self_host_image()` 가 `requests.get()` 으로 원격 이미지를 받아오고, `_fetch_url_content()` 가 URL 유효성 검사 후 `_self_host_image()` 를 호출하는 구조. 원인은 `_fetch_url_content()` 의 URL 유효성 검사가 `http://`/`https://` 문자열만 확인하는 수준이었고, **원격 호스트가 429(Too Many Requests)를 반환해도 5KB 미만 응답이면 fallback 하지 않는** 문제가 있었다.

## 요청

**주제**: `ai-tech-digest` 프로젝트에서 **RSS 피드의 `description` 필드에 포함된 HTML 을 마크다운으로 변환해 LLM 파싱 정확도를 개선한 경험**을 트러블슈팅 형식으로 작성해 줘. (이 프로젝트는 매일 아침 AI 관련 뉴스레터를 생성하는 도구임)

구체적인 상황 (사실 기반):
- 5/16~5/17 RSS 에서 **HTML 엔티티가 포함된 description** 이 유입됨 (`&lt;`, `&amp;`, `&#39;`, `&quot;`).
- LLM 이 이를 그대로 읽어서 **`<` 를 `&lt;` 로 인식** — 파싱 결과에 `&lt;` 문자열이 그대로 남음.
- 이 때문에 **기사 제목/본문 요약이 깨져 보임** (예: "Rust &lt; 1.0" 같이 표시).
- 처음엔 "HTML 태그 제거" 로 접근 → 태그 제거만으로는 부족함을 확인.
- 이후 **`html.unescape()` 적용 + 순서 문제** 를 발견: 태그 제거 → unescape 순서가 맞아야 함.
- 최종적으로 **HTML entity 디코딩 + 태그 제거 파이프라인** 으로 정리.

이 글은 위의 소재를 **하나의 트러블슈팅 섹션**으로 구성해서 써. 그리고 **다른 트러블슈팅 섹션 1개를 더** 추가해. 추가 섹션도 같은 5블록 구조를 따라야 해. 소재는 자유롭게 창작하되, 이 개발 블로그의 주제(ai-tech-digest, jekyll, ruby, github actions, python)와 잘 맞아야 해.

필수 포함해야 할 요소:
- **`_self_host_image()`** — 함수명을 본문에 반드시 포함 (1회 이상)
- **`replication lag 45초`** — 반드시 본문에 포함 (어느 섹션이든)
- **`opengraph`** — 반드시 본문에 포함 (어느 섹션이든)
- **`connection pool 100/100`** — 반드시 본문에 포함 (어느 섹션이든)

이 필수 요소들은 자연스럽게 사고 흐름에 녹아야 하며, 없는 것보다 어색하게라도 있는 게 나을 정도로 취급하라. 절대 키워드 나열처럼 보이면 안 된다.

## 주제

**`auto-anki` — 카드 생성 실패율이 15% 로 치솟던 문제를 `sqlite3_busy_timeout` / `WAL` / `page_size` 조합으로 해결한 건에 대한 회고**

## 핵심 사실 (이 데이터를 기준으로 글을 쓸 것)

- **증상**: 카드 생성 실패율 15%, `database is locked` 에러가 하루 200~300건.
- **환경**: SQLite 파일 하나를 여러 워커가 공유, `check_same_thread=False` 로 동시 접근.
- **첫 가설**: SQLite `busy_timeout` 부족 → `PRAGMA busy_timeout=5000` 설정.
- **결과**: 실패율 15% → 8% 로 절반 감소했지만 여전히 존재. (busy_timeout 으로는 부족)
- **다음 단서**: `database is locked` 에러가 남은 상황에서 `wal_checkpoint(TRUNCATE)` 로그와 `SQLITE_BUSY` 가 동시에 나타난다.
- **진짜 원인**: checkpoint 가 WAL 파일을 비우는 동안 checkpoint 프로세스가 `SQLITE_BUSY` 를 만나 checkpoint 를 재시도. 이 때 WAL 파일이 계속 쌓여서 결국 `database is locked` 발생. → **원인은 "checkpoint 실패 재시도" 와 "쓰기 지연(동기화 지연)" 의 복합**.
- **해결**: `wal_autocheckpoint` 기본 1000 페이지(약 4MB)를 500 페이지로 낮추고, `checkpoint` 를 `busy_timeout` 5초와 함께 주기적으로 호출. WAL 파일 크기를 3~5MB 로 유지.
- **검증**: `wal_size` 추이, `busy` 비율, `checkpoint` 주기, `page_size` 등. 30분 부하 테스트에서 `busy timeout` 0건, `WAL 4MB → 1.8MB` 로 감소.
