오늘은 세 가지를 잡았다. Mac 원격 세션에서 relay 배포와 dmg 빌드가 통째로 멈춘 일, iOS 빌드가 업로드 단계에서 거절당한 일, 그리고 펫 가져오기가 목록에 안 뜨던 버그. 셋 다 처음 세운 가설이 틀렸고, 로그를 다시 뜯어보면서 원인이 뒤집힌 케이스였다.

## Mac 원격 세션 키체인 — relay 배포와 dmg 빌드를 분리한 이유

Mac에 위임한 작업이 0단계에서 멈췄다. `git fetch origin`이 아래 메시지로 죽었다.

```
failed to get: -25308
fatal: could not read Username for 'https://github.com': Device not configured
```

`-25308`은 macOS 오류 `errSecInteractionNotAllowed`다. git이 `osxkeychain` credential helper로 키체인에서 토큰을 못 읽었다는 뜻이다. `security show-keychain-info`를 찍어보니 `User interaction is not allowed`가 그대로 나왔고, `gh auth status`도 `The token in default is invalid`로 실패했다.

**첫 가설**은 단순했다. "키체인이 잠겨 있으니 풀면 되겠지." 사용자에게 풀어 달라고 했고, 사용자가 풀었다고 했다. 다시 위임을 걸었다.

> 다시 시도해도 똑같이 0단계에서 멈췄다. `git fetch`가 같은 `-25308`로 실패했다.

여기서 가설이 흔들렸다. 사용자가 터미널에서 키체인을 풀었는데 왜 같은 오류가 나지? 로그를 다시 보니 위임 작업은 매번 새 원격 세션으로 실행된다. 사용자가 앞에서 풀어 둔 키체인 상태가 새 세션에는 적용되지 않는 구조였다. 키체인은 세션 단위로 잠금이 걸리는데, 위임 작업이 매번 새 셸을 열어서 그랬다.

**해결**은 "키체인이 필요한 작업과 필요 없는 작업을 나누는 것"이었다.

- **relay 배포**: 공개 저장소에서 파일 3개(`relay/main.go`, `relay/main_test.go`, `relay/README.md`)만 받아 컨테이너를 다시 띄우는 일. 키체인이 필요 없다. 공개 저장소는 로그인 없이 clone된다.
- **dmg 빌드와 업로드**: 서명 인증서, 공증 프로필(`lepons`), GitHub 토큰이 전부 키체인에 있다. 위임으로는 불가능.

relay는 위임으로 돌렸고 17:19에 중계 컨테이너만 새로 시작됐다. cloudflared는 손대지 않았고, `https://relay.lepons.app/health`가 200을 돌려줬다. dmg는 사용자가 키체인을 푼 같은 터미널에서 직접 실행하도록 명령을 넘겼다.

**검증**은 relay 컨테이너 재시작 시각, health 응답 200, cloudflared 무변경까지 확인했다. dmg는 실제로 그 자리에서 빌드가 돌았고, 이후 서명/공증 검사까지 통과했다. 남은 과제는 "위임 작업이 매번 새 세션이라는 전제"를 다른 자동화에도 똑같이 적용하는 것이다. 키체인을 쓰는 작업은 위임에 넣으면 안 된다는 걸 이번에 확실히 배웠다.

## iOS 빌드 21 업로드 실패 — true로 바꾼 게 오히려 원인이었다

빌드 21이 EAS에서는 "FINISHED"로 끝났는데 App Store Connect 업로드 단계에서 "실패"로 떨어졌다. TestFlight에 안 올라왔다.

**첫 가설**은 "11/06에 암호화 설정을 true로 바꾼 게 문제겠지"였다. 폰과 PC 사이 메시지를 앱이 직접 암호화하니까 정직하게 true로 표시한 거였는데, 그렇게 표시하면 Apple이 먼저 암호화 문서를 받아 승인해야 한다는 걸 놓쳤다. 오류 코드는 90592였고, App Store Connect의 "앱 암호화 문서" 칸은 비어 있었다.

그래서 암호화 문서 양식을 작성하기 시작했다. 1페이지에 앱 용도, 2페이지에 알고리즘 종류(표준 암호화), 3페이지에 프랑스 배포 여부(아니요)를 넣었다. 그런데 마지막 페이지에서 Apple이 예상 밖의 결론을 냈다.

> "답변에 따라서 문서를 업로드할 필요가 없습니다. Info.plist에서 암호화를 사용하지 않음을 명시하면 매번 암호화 질문에 답변하지 않아도 됩니다."

여기서 원인이 뒤집혔다. 표준 알고리즘만 쓰고 프랑스에 배포하지 않으면 Apple 기준으로는 **면제 대상**이다. 이 경우 `ITSAppUsesNonExemptEncryption`은 false가 맞는 값이다. 11/06에 true로 바꾼 게 오히려 업로드 거절의 원인이었다.

**해결**은 `mobile/app.json`의 값을 false로 되돌리는 것이었다. 빌드 21과 코드는 같고 Info.plist 값 하나만 다르다. 빌드 22로 다시 올렸더니 업로드가 통과했고, 저장소에도 false로 확정 커밋(`d75d4e2`)을 남겼다.

**검증**은 빌드 22가 TestFlight에 정상 처리된 것까지 확인했다. 남은 과제는 프랑스 배포다. 프랑스에 내보내려면 별도 신고서가 필요해서, 다음 App Store 제출 전에 "가격 및 사용 가능 여부"에서 프랑스를 빼야 한다. 커밋 메시지와 인계 문서에 같이 적어 뒀다.

## 펫 가져오기 목록 버그 — 펫이 켜져 있을 때만 안 뜨던 이유

커스텀 펫을 가져왔는데 "펫 고르기" 목록에 안 뜬다는 리포트가 왔다. 그런데 설정 창을 닫았다 다시 열면 나타난다. 즉 데이터는 들어갔는데 화면 갱신만 안 된 상태였다.

**첫 가설**은 "임포트 자체가 실패했거나 폴더 형식이 안 맞는 거겠지"였다. `importPet`가 `pet.json`이나 상태별 이미지 파일을 못 찾으면 에러를 돌려주니까. 그런데 펫이 실제로 입혀지기까지 했다는 건 임포트가 성공했다는 뜻이다. 데이터는 들어갔는데 목록만 안 뜨는 거라 가설이 틀렸다.

코드를 다시 봤다. `cockpit/src/main/index.ts`의 `importPetFolder`가 `importPet` 호출 후 `event.sender.send(channels.powerAction, "pet", "on")`를 보낸다. 이 신호가 설정 창의 펫 목록을 다시 그리는 역할도 겸하고 있었다.

> 그런데 이 신호가 `if (!petWindow)` 조건 안에서만 나가고 있었다. 펫이 이미 켜져 있으면 신호가 안 가고, 그래서 목록이 갱신되지 않았다.

**해결**은 조건을 제거하는 한 줄이었다. 가져오기가 끝나면 항상 신호를 보낸다. 펫이 이미 켜져 있으면 "켜기" 동작은 아무 일도 하지 않고, 목록만 다시 그린다. 타입 검사와 테스트 948개가 통과했다.

**검증**은 테스트까지였고, 실제 앱에서 가져오기 버튼을 눌러보지는 않았다. 그건 1.9.8 릴리스에 넣었고, 1.9.7과 패치 지문이 같아서 기존 사용자는 작은 패치로 업데이트된다. 남은 과제는 실제 앱에서 눌러 확인하는 것과, 같은 패턴의 다른 IPC 신호에도 조건이 걸려 있는지 훑는 것이다.
