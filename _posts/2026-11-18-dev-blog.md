오늘은 세 가지를 잡았다. 배포가 파일 접근 단계에서 막힌 일, 프로덕션 화면에서 후보 목록이 통째로 사라진 일, 터미널 창이 무너진 일. 첫 번째는 권한 문제라고 봤는데 이미 떠 있던 프로세스가 원인이었고, 두 번째는 프론트가 아니라 DB 데드락이었고, 세 번째는 메모리 탓이라고 단정했다가 하루 전에 넣은 코드를 다시 뜯어보게 됐다.

## 사주 배포 — 파일을 못 읽은 건 권한이 아니라 11월 16일에 켜 둔 tmux였다

배포 전 점검으로 `git status --short oyeon-web`을 돌렸는데 바로 죽었다. `fatal: Unable to read current working directory: Operation not permitted`, 종료 코드 1이었다. Node로 문법 검사를 돌린 쪽은 더 노골적으로 `EPERM: operation not permitted, uv_cwd`를 뱉었다. `wrangler.toml`을 읽으려 해도 같은 EPERM이었다. 그런데 `pwd`는 `~/Downloads/사주`를 정상으로 찍었다. 경로가 틀린 건 아니라는 뜻이었다.

**첫 가설은 샌드박스**였다. 도구 실행 환경이 다운로드 폴더를 막는 줄 알고 샌드박스를 껐는데, 오류가 한 글자도 안 바뀌었다. 그래서 범위를 좁혀 봤다. `ls -ld ~/Downloads`는 `drwx------`로 잘 읽혔고, `ls ~/Downloads/사주`만 `Operation not permitted`로 막혔다. `cd /tmp`로 나가서 `git -C ~/Downloads/사주 status`를 쳐도 128이었다. git 문제가 아니라 폴더 접근 자체가 막힌 상태였다.

그다음이 진짜 전환점이었다. 폴더 접근 권한을 켜 줬는데도 같은 오류가 그대로 났다.

> 권한을 새로 줬는데도 안 된다면, 의심할 건 권한 값이 아니라 그 권한을 확인한 시점이다.

macOS는 프로그램이 시작될 때 권한을 확인한다. 이 세션은 **11월 16일부터 켜져 있던 tmux 안**에서 돌고 있었다. 그래서 터미널 앱만 껐다 켜는 걸로는 부족하고, tmux 자체를 새로 띄워야 했다. 터미널 앱을 완전히 종료하고 `tmux kill-server`로 서버를 내린 뒤 새 tmux에서 작업 세션을 다시 열었다.

권한이 돌아온 뒤에는 순서대로 밀었다. 실서버 DB에는 `limits` 테이블을 추가했고 기존 데이터는 건드리지 않았다. 변경분을 커밋 `9da4f19`로 `release_st`에 푸시하고 배포했다.

**검증**은 실제 사이트에서 했다. 새 버전 `v=20261118a`가 나가고 진행률 팝업과 "결제한 풀이 이어서 보기" 버튼이 페이지에 들어간 걸 확인했다. 개인정보 처리방침에 IP 호출 제한 문단도 반영됐다. 결제 없이 미리보기를 한 번 요청해 보니 200으로 AI가 쓴 풀이가 왔고 29초 걸렸다. 새로 넣은 IP 호출 수 세기 단계에서 오류가 없었다는 뜻이다. 다만 결제 풀이는 실제 결제가 필요해서 아직 실서버에서 못 봤다. 진행률 팝업, 결과 저장·공유, 인앱 브라우저 결제도 같은 이유로 미확인이다.

## rafeed 후보 목록 — 화면이 아니라 서버에서 터진 Postgres 데드락

배포된 페이지에 들어가면 후보 목록 자리에 "영상 후보를 불러오지 못했습니다"만 떴다. `loadPosts`가 `/api/posts?days=14`를 부르고 실패하면 그 문구로 갈아끼우는 구조라, 처음엔 렌더링 JS를 의심했다. 그런데 API는 200이었고, 실제 데이터를 넣고 렌더 코드를 그대로 돌려도 정상으로 그려졌다. 화면 코드는 유죄가 아니었다.

그래서 **간헐적 서버 오류** 쪽으로 방향을 틀어 Vercel 로그를 열었다. 거기서 `/api/topics` 요청이 `DeadlockDetected`로 실패한 기록을 찾았다. 연결마다 스키마 확인이 붙는 자리였다.

원인은 이렇게 맞물려 있었다. 페이지가 뜰 때 화면이 서버로 요청 6개를 동시에 보낸다. 서버는 연결할 때마다 "테이블 구조가 최신인지" 확인하고 고치는데, 이 확인은 원래 서버가 처음 뜰 때 한 번만 돌게 설계된 것이다. 문제는 Vercel 서버가 한동안 안 쓰이면 꺼졌다가 다음 접속에 새로 뜬다는 점이었다. 콜드 스타트에서 요청 6개가 동시에 스키마 확인을 실행했고, 서로가 잡은 테이블 잠금을 기다리다 DB가 그중 하나를 강제로 실패시켰다. 실패한 요청이 후보 목록 요청이면 그 문구가 뜬 거다.

재현은 간단했다. 같은 상황을 직접 만들어 보니 동시 연결 18번 중 6번이 같은 오류로 죽었다.

**해법**은 `src/rafeed/db.py`에서 스키마 확인을 시작하기 전에 Postgres 잠금 하나를 먼저 잡게 하는 것이었다. 서버가 여러 대 떠 있고 맥 작업이 같이 들어와도 한 줄로 서서 하나씩 확인하게 만들었다. 확인만 직렬화하면 되니 요청 자체를 줄일 이유는 없었다.

| 구분 | 이전 | 이후 |
|---|---|---|
| 동시 재현 | 18번 중 6번 실패 | 36번 전부 성공 |
| 테스트 | — | 273개 통과 |
| 실서버 동시 요청 | — | 60개 전부 정상 응답 |

**남은 과제**는 응답 크기다. 후보 목록 요청 하나가 2.1MB, 주제 1,342건을 받는다. 수집처를 붙이면서 건수가 늘어난 결과다. 지금은 0.5초 안에 오지만 휴대폰 데이터로 보면 체감이 다를 수 있어서, 화면에서 쓰지 않는 필드를 빼는 걸 다음 후보로 잡아 뒀다.

## Lepons 터미널 붕괴 — 메모리 탓이라고 했지만 범인은 스크롤 막대 코드였다

증상이 이상했다. 원격 터미널 영역이 통째로 비고 탭 줄도 사라졌다. 대신 화면 중간(y≈323)에 가로선이 한 줄 그어져 있는데, 그 선이 왼쪽 패널의 항목 줄까지 가로질렀다. 왼쪽 패널에서는 "연결됨"이 한 글자씩 세로로 줄바꿈돼 있었다.

처음엔 **메모리 부족**으로 판단했다. 14GB 중 남은 게 1.1GB였고, VS Code 14개 창이 2.7GB, 브라우저 26개 탭이 2.5GB를 쓰고 있었다. 여기에 Lepons가 0.6GB를 얹고 있었으니 그래픽 처리가 끊겼다고 본 거다. 창을 최대화해 다시 그리게 하라거나, 안 쓰는 창을 닫으라고 답했다. **이 판단은 틀렸다.**

다시 본 건 하루 전에 넣은 스크롤 막대 코드(`e74e3a1`)였다. 앱은 화면에 안 보이는 터미널(뒤쪽 탭, 백그라운드 세션)을 원래 왼쪽 -9999px에 숨겨 둔다. 그런데 스크롤 막대를 붙이는 코드가 원격 tmux 터미널의 위치 방식을 바꿔 버렸고, 그 바람에 숨겨 둔 원격 터미널이 다시 화면 배치 안으로 끌려 들어왔다.

> 숨은 터미널이 배치 안으로 들어오면 너비 100%짜리 칸을 차지한다. 그 한 칸이 왼쪽 패널과 터미널 영역을 옆으로 밀어낸다.

"연결됨"이 세로로 줄바꿈된 것도, 터미널이 사라진 것도, 가로선이 패널까지 관통한 것도 전부 이 한 칸 때문이었다. 9시쯤 앱을 다시 켜면서 원격 백그라운드 세션이 한꺼번에 만들어져 갑자기 드러난 것이었다.

**수정**은 스크롤 막대 코드가 터미널 위치를 아예 건드리지 않게 하는 것이었다. 숨은 터미널은 계속 화면 밖에 두고, 화면에 보이는 터미널에만 스크롤바 기준 위치를 준다(`9b16d5a`). 타입 검사와 테스트 1043개는 통과했다. 실제 앱에서 화면이 돌아오는지는 그 시점에 확인하지 못했고, 빌드와 설치를 거친 뒤에야 붕괴가 재현되지 않는 걸 봤다.

## Markdown 미리보기 스크롤바 — 앱 CSS가 iframe 안까지 닿지 않았다

붕괴를 고친 빌드를 설치한 뒤 새 증상이 왔다. `.md` 파일을 미리보기로 열면 스크롤바 배경만 흰색으로 나왔다. Markdown과 HTML 미리보기는 앱 문서가 아니라 sandbox가 걸린 별도 iframe 안에서 그려진다. 앱의 스크롤바 색 변수는 그 문서에 적용되지 않으니 크롬 기본 스크롤바가 나올 수밖에 없었다.

iframe 쪽 문서에 앱과 같은 색 변수를 넣어 테마를 따라가게 고쳤다(`7ec9a71`). 같은 방식으로 그려지는 안내 화면도 덩달아 고쳐졌다. 그래서 드롭다운 목록이나 날짜 입력칸 같은 브라우저 기본 부품이 어두운 테마에서도 밝게 그려질 수 있었다. 이건 별도 커밋으로 처리했다.

**검증**은 코드로만 했다. 실제 화면은 설치 후에 봐야 한다. PDF 뷰어와 아이콘 툴팁은 OS와 크롬이 직접 그리는 영역이라 앱에서 바꿀 수 없어서 손대지 않았다.
